# Демо mention-agent: 21.10, 18:00 МСК, 3–4 минуты

Один живой прогон LangGraph-агента на локальных моделях: 4 упоминания, ~75–90 секунд.

## Подготовка за 15 минут до показа

1. **Питание и сон.** Mac подключён к зарядке, крышка открыта. Во время прогона Mac не должен засыпать:
   команда ниже запускается через `caffeinate -i`.
2. **Ollama.** Если не запущена: `open -a Ollama`. Проверка: `curl -s localhost:11434/api/tags` отвечает JSON.
3. **Терминал.** Открыть папку проекта и активировать окружение:
   ```bash
   cd ~/PycharmProjects/mention-agent && source .venv/bin/activate
   ```
4. **Прогрев.** Загружает модель в память на 30 минут, чтобы не было холодного старта:
   ```bash
   STRONG_MODEL=qwen2.5:3b python cli.py --warmup
   ```
   Затем один пробный прогон (команда ниже): он заодно прогревает кэш промптов. Если пробный прогон уложился в 90 с, всё готово.
5. **Экран.** Шрифт терминала 18–20 pt (⌘+), окно на весь экран, `clear` перед показом.
   Закрыть браузер, IDE, Docker, Telegram и уведомления (Фокусирование → «Не беспокоить»): на CPU каждый процесс крадёт секунды.
6. **Во второй вкладке** открыть `agent/graph.py` (docstring со схемой графа вверху файла) и `demo_backup.txt` на случай сбоя.

## Команда для показа

```bash
STRONG_MODEL=qwen2.5:3b caffeinate -i python cli.py --file data/mentions_live.json
```

Замеры после прогрева (Mac Intel, 16 ГБ, CPU): 75,8 с / 91,6 с / 79,8 с. Маршрутизация во всех прогонах одинаковая.

**Если прогон сломался или завис дольше 2 минут:** Ctrl+C, `cat demo_backup.txt` — это вывод удачного прогона на той же машине.
`demo_7b.json` — тот же набор на сильной модели qwen2.5:7b (~5 минут): показать, если спросят про качество планов.

## Вероятные вопросы CEO

**Почему локальные модели?**
Ноль затрат на токены и данные клиентов не уходят наружу. Код от этого не зависит: та же программа переключается на OpenAI-совместимый API одной переменной `LLM_PROVIDER=openai`.

**Как ограничен цикл инструментов?**
Жёстким лимитом `MAX_TOOL_STEPS` (по умолчанию 4). Если модель хочет ещё, граф всё равно идёт к плану, а упоминание помечается `tool_limit_reached` для человека. Плюс правило в коде: без плейбука план не строится, недостающий раздел подтягивается автоматически.

**Как валидируется вывод модели?**
Каждый ответ проходит строгую схему Pydantic (типы, допустимые значения, длины, сроки 1–168 ч), а раздел плейбука сверяется со списком существующих. При ошибке модели возвращается текст ошибки и даётся один ретрай; если не вышло, упоминание уходит на ручную проверку. Модель не может «придумать» формат.

**Зачем каскад?**
Большая часть упоминаний — мусор и позитив, им не нужна дорогая модель. Правила отсекают мусор бесплатно, дешёвая модель закрывает простое, сильная тратится только на жалобы. На этом наборе это больше половины времени; с API — те же проценты в деньгах.

**Как масштабировать?**
Упоминания независимы, поэтому обработка параллелится: очередь плюс несколько воркеров. Модели выносятся на GPU-сервер (vLLM/Ollama) или в облачный API, код не меняется. Префильтр и дешёвая модель снимают основной поток, поэтому сильных вызовов растёт меньше, чем упоминаний.
